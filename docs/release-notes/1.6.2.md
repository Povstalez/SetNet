# 1.6.2 — the client receive path stops allocating twice per event

`SetNet` **1.6.2**. Every companion package is unchanged.

## Why

A Unity client taking hundreds of push events per frame turned two "invisible" allocations into a steady garbage
stream. Both sat on the path every single inbound event walks, and one of them was introduced by an optimization
that was correct on the wrong runtime.

## The enumerator that is a struct — but not everywhere

1.3.0 replaced `bucket.Values` (which builds a snapshot list per access) with a `foreach` over the
`ConcurrentDictionary` itself, and left a comment stating that its enumerator is a struct and takes no lock.

That is **true on .NET 9+**, which added a public struct enumerator. It is **false on the Mono runtime Unity
ships**: `GetEnumerator()` there returns `IEnumerator<KeyValuePair<K,V>>` backed by a compiler-generated class.
Verified by disassembling Unity's own `mscorlib.dll` — the iterator is `.class ... extends System.Object` — and the
shipped `SetNet.dll` calls it through `callvirt`. So on the runtime that needed the optimization most, it was one
heap allocation per delivered event, which for a small event is larger than the payload itself.

`ProtocolSubscriptionRegistry` now keeps a copy-on-write snapshot array beside the dictionary and delivers through
a plain `for`. That allocates nothing on any runtime, and rebuilding costs nothing that matters: subscriptions
change a handful of times per session, deliveries happen thousands of times per second. The snapshot is published
with `Volatile.Write`, so a subscription taken out mid-dispatch is tolerated exactly as before — the walker
finishes with the list it started on.

## The envelope was copied twice

1.3.0 removed the copy inside `ProtocolEnvelope.Decode`. One level up, `CommandExecutor.DispatchAsync` still did:

```csharp
ProtocolDispatcher.DispatchClientAsync(_runtime, _runtime.Deserialize<byte[]>(data));
```

`data` already holds the frame. `Deserialize<byte[]>` produced a second array holding byte for byte the same
content, minus the two or three bytes of wrap header — one throwaway array per delivered event, so that the
dispatcher below could read the envelope through a window anyway.

The header is now skipped in place:

```csharp
int skip = WrapHeaderSize(data);
if (skip >= 0)
    return ProtocolDispatcher.DispatchClientAsync(_runtime, data.AsMemory(skip));
```

`WrapHeaderSize` derives the length from `IBinaryFrameSerializer.MeasureBinaryFrameHeader` rather than from
knowledge of any particular format: for a given total length exactly one header size `h` satisfies
`MeasureBinaryFrameHeader(total - h) == h`. A serializer that does not frame binary payloads (JSON and friends)
returns -1 and keeps the old path, unchanged.

## New API

**`ProtocolDispatcher.DispatchClientAsync(SetNetRuntime, ReadOnlyMemory<byte>)`** — same routing as the array
overload, but the caller keeps ownership of the buffer.

**`ProtocolEnvelope.DecodeHeader(ReadOnlySpan<byte>, …)`** and **`ProtocolEnvelope.BodyOf(ReadOnlyMemory<byte>)`** —
the header and body readers, over a window.

The window must stay valid for the duration of the call and no longer. Push events are consumed by their
subscribers before the call returns, so a window is safe for them. **Replies and errors still get an array of their
own** — they are handed to a caller waiting on another thread. That copy is the ownership boundary, not an
oversight.

## Compatibility

Purely additive; the wire format is unchanged and no server needs updating. `OnRaw` subscribers still receive a
`byte[]` with the same guarantees, and the `Add`/`AddMemory` split behaves as before.

## Tests

322 tests: 319 passing, 3 skipped (they need a live Redis). No behavioural change to assert — the value is in what
is *not* allocated, and the existing dispatch/subscription coverage is what proves the rewrite routes identically.
