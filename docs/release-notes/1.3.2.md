# 1.3.2 — the route a mover walks is readable

`SetNet.Locomotion` **1.3.2**, `SetNet.PathFinding` **1.3.2**. Every other package is unchanged and stays where it
was — **including the core**: `SetNet` remains 1.3.0, because nothing in it changed.

> The publish workflow used to require the release tag to equal the core package version, which quietly assumed
> every release touches the core. It now requires the tag to match at least one bumped project, so a release like
> this one — companion packages only — passes the guard instead of demanding an empty bump of `SetNet`.

## Why

`Mover` computed a route and then hid it. The only thing visible from outside was `Destination`, which pushed every
server into the same shape: replicate the point, let each client re-run the search. That is the classic MMO trade,
and it is fine until a crowd — then N clients each pay for one pathfinding run per moving entity, and the orders
arrive together, so the runs pile into a single frame.

The server already has the answer. It just had no way to hand it over.

## New API

**`Mover.Waypoints`** — `IReadOnlyList<Vec3>`, the route currently being walked; empty when idle.

**`Mover.WaypointIndex`** — how many waypoints are already behind. `Waypoints[WaypointIndex]` is the point the
mover heads toward right now, so the slice from there on is the remainder — which is what a client that showed up
in the middle of a walk needs, rather than the whole route.

**`PathFollower.Route`** and **`PathFollower.Index`** — the same two facts one level down, for anyone driving a
follower directly.

```csharp
loco.Started += m =>
{
    // Was: send m.Destination and let the client re-path.
    // Now: send the polyline that was already computed.
    Replicate(m.Owner, m.Waypoints);
};
```

## Compatibility

Purely additive. Nothing was removed, renamed, or changed in behaviour — existing code that replicates
`Destination` keeps working untouched, and upgrading needs nothing beyond the version bump.

One rule for the new members: the list belongs to the pathfinder, and the next `GoTo` replaces it. Read it when the
order fires; do not hold it.

## Tests

305 tests: 302 passing, 3 skipped (they need a live Redis / a TLS certificate). Four are new — `MoverRouteTests`
covers the idle case, that the route ends at the destination, that the index advances as waypoints are consumed,
and — the one that matters — that the published route is *the* route being walked, by stepping the mover through a
walled field and asserting every intermediate position stays on the polyline it handed out. Verified by mutation:
publishing a plausible-looking straight line from position to destination instead of the follower's own route makes
exactly that test fail.
