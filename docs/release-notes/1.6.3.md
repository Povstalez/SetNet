# 1.6.3 — `ReceiveAsync` returns `ValueTask`

`SetNet` **1.6.3**. Every companion package is unchanged.

## Why

`ITransportConnection.ReceiveAsync` is called **once per message**, not once per socket read. During a burst — the
common game-tick pattern, many small messages arriving together — the next frame is usually already sitting in the
receive buffer, so the call completes synchronously and never suspends.

A `Task`-returning method allocates on that path regardless. The BCL caches `Task<T>` results only for `bool`,
small `int` values and null references; a `TransportMessage?` carrying a value is none of those, so the fast path
falls through to `new Task<TResult>(result)` every time.

## What changed

```csharp
// Was
Task<TransportMessage?> ReceiveAsync(CancellationToken ct = default);
// Now
ValueTask<TransportMessage?> ReceiveAsync(CancellationToken ct = default);
```

The interface and all nine implementations — TCP, UDP client/server, `Both`, InMemory, WebSockets, and the two
Unity WebSocket connections. Every caller inside the library awaits the result immediately, so nothing else had to
move.

## Compatibility

**Breaking for anyone implementing `ITransportConnection` or storing the returned task.** Implementations change
`Task` to `ValueTask` in the signature; `async` bodies need no other edit. Callers that only `await` need no change
at all.

The usual `ValueTask` rules apply and are not optional: await it exactly once, do not store it, do not combine it
with `Task.WhenAny`. Call `AsTask()` first if you need any of that.

## Not in this release: pooling the receive buffer

`PacketBuilder` still allocates a `byte[]` per frame, and it stays that way deliberately. There is no safe point to
return a pooled buffer today, for two independent reasons:

- `BaseSocket.DispatchAsync` hands the array to `OnRawFrame`, whose documented contract promises *"a fresh
  per-message array; safe to keep or forward"* — and that is load bearing: `SetNet.Gateway` forwards it byte for
  byte, `SetNet.Cluster` too;
- with the default `SequentialDispatch = false`, handlers are dispatched without waiting, so nothing knows when the
  array is free.

An opt-in flag would not be an acceptable shortcut: getting it wrong does not throw, it silently overwrites another
message — the hardest class of bug to diagnose. Pooling the receive buffer needs explicit buffer ownership through
the whole dispatch chain, which is a design decision rather than an optimization. See `docs/PERFORMANCE.en.md`, P4/P5.
