# SetNet 1.3.0 — allocation-free client push events

> **Correction (1.6.2).** Point 2 below — "the dispatcher now enumerates the dictionary itself (struct enumerator)"
> — holds on .NET 9+ but **not on the Mono runtime Unity ships**, where `ConcurrentDictionary.GetEnumerator()`
> returns an interface backed by a class, i.e. one allocation per delivered event. 1.6.2 replaced it with a
> copy-on-write snapshot array. The rest of this release stands. See
> [1.6.2](1.6.2.md).

Packages: **SetNet 1.3.0**, **SetNet.MessagePack 1.2.0**.

Additive release: no API was removed or changed in meaning. Existing code — including every SetNet module —
behaves exactly as before, with no recompilation needed beyond the version bump.

## Why

Push events are the one path a game client walks hundreds of times per *frame*. Three allocations that are
invisible in request/response traffic added up to a steady garbage stream there — measured in a Lineage 2 client
with ~700 visible actors as tens of kilobytes per frame, enough to keep the incremental collector busy for
milliseconds of every frame.

## What changed

**1. The assembly scan no longer polls.** `ClientEventDiscovery.EnsureDiscovered` runs on every dispatched event
and called `AppDomain.CurrentDomain.GetAssemblies()` just to compare the count — a call that allocates a fresh
array holding every loaded assembly. It now subscribes to `AppDomain.AssemblyLoad` once and checks a flag; the
steady state is a single `volatile bool` read. A module enabled later is still discovered — the CLR reports its
assembly load.

**2. Subscriber iteration no longer snapshots.** `ConcurrentDictionary.Values` builds a list on every access; the
dispatcher now enumerates the dictionary itself (struct enumerator, no lock, tolerant of concurrent
subscribe/unsubscribe).

**3. Event bodies are no longer copied out of the frame.** `ProtocolDispatcher` reads only the fixed header and
hands the body to subscribers as a `ReadOnlyMemory<byte>` window onto the received frame. Replies and errors
still get an array of their own — they outlive the call, because a waiting caller receives them.

## New API

- `IMemorySerializer` (`SetNet.Messaging`) — optional companion to `ISerializer`:
  `T Deserialize<T>(ReadOnlyMemory<byte> data)`. Implemented by `MessagePackNetSerializer`.
- `ProtocolSubscriptionRegistry.AddMemory(channel, op, Action<ReadOnlyMemory<byte>>)` — subscribe without asking
  for an array.
- `ProtocolSubscriptionRegistry.Dispatch(channel, op, ReadOnlyMemory<byte>)` — deliver a body held in a larger
  buffer.
- `ProtocolEnvelope.DecodeHeader(...)` / `ProtocolEnvelope.BodyOf(frame)` — header-only decode plus a window onto
  the body.

`client.On<T>(...)` picks the zero-copy path automatically when the registered serializer implements
`IMemorySerializer`, and falls back to the array path otherwise. Callers see the same decoded message either way.

## Compatibility

- `OnRaw` subscribers still receive a `byte[]` — now materialised **lazily**, only when such a subscriber exists
  for that channel/op. Every bundled module (Ping, Relay, NatPunch, Trade, Rooms, …) subscribes with `OnRaw` and
  is unaffected.
- Declarative `[Event]` handlers go through the array path as before.
- A custom `ISerializer` without `IMemorySerializer` keeps working unchanged.

**One rule for the new path:** the memory window is valid only for the duration of the callback. Decode from it;
do not store it. A subscriber that needs to keep the bytes should use `Add`/`OnRaw` and get its own array.

## Tests

`tests/SetNet.UnitTests/ProtocolEventDispatchTests.cs` covers both subscription shapes, disposal, and — via
`MemoryMarshal.TryGetArray` — asserts that a memory subscriber really receives a slice of the received frame
rather than a copy. That assertion fails if the dispatcher ever goes back to copying.
